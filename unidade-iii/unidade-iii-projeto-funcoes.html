Contexto

Este é o mesmo cadastro de alunos da Unidade II — nomes como strings de verdade, busca parcial, correção, contagem de letras. Só que lá ainda não existiam funções: todo o código de cada opção do menu morava dentro do próprio switch, direto no main, e nomes, ras e totalAlunos eram variáveis globais.

Agora que Semana 1 e Semana 2 cobriram protótipo/definição/chamada, parâmetros por valor, escopo, passagem por referência e vetores como parâmetro, chegou a hora de refatorar esse cadastro: cada opção vira uma função própria, com parâmetros — e as variáveis globais somem do programa.

A avaliação considera tanto o planejamento (aula 9) quanto o código final (aulas 10-12).

Objetivos de aprendizagem

  • Protótipo, definição e chamada de funções próprias — cada opção do menu (e mais algumas) vira uma função, declarada antes do main e definida depois dele.
  • Eliminação de variáveis globais: nomes, ras e totalAlunos passam a ser locais ao main, chegando às demais funções exclusivamente por parâmetro.
  • Passagem por valor x por referência: a maioria dos parâmetros (um RA, uma letra) é passada por valor. Quando uma função precisa alterar, para quem a chamou, uma variável que não seja vetor, ela só consegue fazer isso recebendo essa variável por referência, com um ponteiro. Cabe ao trio identificar, para cada função que for propor, se algum parâmetro se encaixa nesse caso.
  • Vetores como parâmetro: nomes e ras são passados para várias funções — e, por decaírem para ponteiro automaticamente, toda função que os recebe já trabalha por referência sobre o vetor original. Isso exige passar o tamanho útil (totalAlunos) como parâmetro separado.
  • Eliminar duplicação com funções auxiliares: o laço que procura um aluno pelo RA, que no gabarito da Unidade II aparecia copiado em dois case diferentes, agora vira uma única função (buscarIndicePorRA).

As funções do sistema

O comportamento visível ao usuário — o menu e as 6 opções — não muda em relação à Unidade II. O que muda é a organização interna: em vez de código solto dentro de um switch, temos 8 funções com contrato (protótipo) bem definido.

Regra prática

Para cada função, decidam e justifiquem: quais dados de main ela precisa enxergar (viram parâmetros) e se algum desses parâmetros precisa ser alterado e "devolvido" para quem chamou — só nesse caso ele deve ser passado por referência, via ponteiro.

Requisitos para o design das funções

Diferente da Unidade II, aqui não fornecemos o main, o menu nem os protótipos prontos: é o trio que deve propor a assinatura de cada função (nome, parâmetros e tipo de retorno) — não só implementar o corpo. Ao decidir cada assinatura, sigam estas regras:

  • Nenhuma variável global. nomes, ras e totalAlunos (e quaisquer outras variáveis de estado do cadastro) devem ser declaradas dentro de main e chegar a qualquer outra função exclusivamente por parâmetro. Nenhuma dessas variáveis pode ser declarada fora de main
  • Todo parâmetro começa como candidato a passagem por valor. Só promovam um parâmetro a passagem por referência (ponteiro, tipo *nome) quando a função realmente precisar alterar, para quem a chamou, uma variável que não seja vetor
  • Vetores já decaem para ponteiro automaticamente ao serem passados como parâmetro — toda função que os recebe já enxerga o vetor original, sem precisar de * explícito na assinatura. Ainda assim, como o vetor não "sabe" seu próprio tamanho, o tamanho útil (totalAlunos) deve viajar junto, como parâmetro separado, em toda função que precise percorrer os vetores
  • Protótipo antes do main, definição depois dele, para todas as funções que criarem
  • Nenhuma lógica duplicada. Se perceberem que duas funções diferentes precisam do mesmo laço de busca, extraiam essa lógica para uma função auxiliar reaproveitada pelas duas — não copiem o laço
  • Pensem também na granularidade de cada parâmetro: nem toda função que lida com nomes precisa receber o cadastro inteiro — algumas operam sobre um único nome

No rascunho da aula 9 (ver Entregáveis), documentem a assinatura proposta para cada função e, para cada parâmetro, a justificativa de por que ele é por valor ou por referência.

Requisitos técnicos obrigatórios

  • Nenhuma variável global. nomes, ras e totalAlunos são locais a main e chegam às funções só por parâmetro
  • As 8 funções da tabela implementadas, com protótipo antes do main e definição depois dele
  • Cada parâmetro passado por valor ou por referência de acordo com a real necessidade da função: por padrão, valor; referência (ponteiro) apenas quando a função precisar alterar, para quem chamou, uma variável que não seja vetor
  • buscarIndicePorRA implementada uma única vez e chamada tanto por corrigirNome quanto por contarOcorrenciasLetra — sem duplicar o laço de busca
  • contarLetraNoNome recebe um único vetor de char e percorre-o manualmente (sem strchr/strstr)
  • MAX_ALUNOS e TAM_NOME continuam como constantes (#define)
  • Leitura de nome aceita nomes compostos; uso de no mínimo strcpy e strstr (herdado da Unidade II)
  • Programa não estoura vetor nem trava com entrada razoável
  • Menu roda em loop até a opção "Sair"

Desafios extras e erros comuns

Desafios extras (opcional, para quem terminar antes)

  • Escrever void trocarAlunos(char nomes[][TAM_NOME], int ras[], int i, int j) que troca de posição os dados de dois alunos, e usá-la para ordenar a listagem por nome com bolha (strcmp dentro do algoritmo de ordenação)
  • Escrever int existeNomeDuplicado(char nomes[][TAM_NOME], int totalAlunos, char novoNome[]) usando strcmp, chamada dentro de cadastrarAluno para impedir nomes repetidos
  • Escrever void gerarEtiqueta(char destino[], char nome[], char turma[]) usando strcat (com o cuidado do espaço, que não é automático)
  • Escrever int indiceNomeMaisLongo(char nomes[][TAM_NOME], int totalAlunos) usando strlen, numa nova opção de menu
  • Tornar a busca (opção 3) sem diferenciar maiúsculas de minúsculas

Erros comuns — de olho nisso

Esquecer o * ao alterar um parâmetro passado por referência. Se decidirem passar totalAlunos (ou qualquer outra variável) por referência para poder alterá-la dentro de uma função, escrever totalAlunos++ direto não funciona como esperado — isso incrementa o ponteiro, não o valor apontado. O certo é (*totalAlunos)++ ou *totalAlunos = *totalAlunos + 1.

Passar o vetor mas esquecer o tamanho. nomes e ras não "sabem" quantos alunos estão cadastrados — por isso totalAlunos sempre viaja junto, como parâmetro separado, em toda função que precisa percorrer os vetores.

Recriar as variáveis como globais "pra facilitar". Declarar nomes, ras ou totalAlunos fora de main anula o objetivo do projeto — a ideia é justamente aprender a fazer esses dados circularem só por parâmetro.

Confundir um ponteiro para uma única variável (ex.: int *variavel) com um vetor (ex.: int vetor[]) na assinatura. São duas formas diferentes de "passagem por referência": uma explícita (o *, para uma única variável), outra implícita (o decaimento automático de vetor para ponteiro).

Chamar uma função antes do protótipo dela existir no arquivo. Sem o protótipo lá em cima, o compilador não conhece a função na hora da chamada dentro de main — mesmo que a definição exista mais abaixo no arquivo.

Ainda valem

Os erros comuns de string da Unidade II continuam relevantes: scanf(" %[^\n]", nome) para nome composto, strcmp (não ==) para comparar conteúdo, espaço manual antes de strcat, e cuidado para não estourar TAM_NOME num strcpy.
